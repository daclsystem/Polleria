Revisión: 21 de noviembre de 2026, hora de Lima.

RESULTADO
La API fue actualizada en /opt/polleria/api y está en línea. Se inició sesión con el acceso facilitado por el propietario y se confirmó visualmente en System: “Emisión activa” y “Certificado guardado en el servidor: certificado.p12”. El aviso “API pendiente de actualizar” ya no aparece. La configuración y el certificado permiten habilitar la emisión sin key. La base de datos y el certificado original se conservaron. Esto no acredita todavía la aceptación de un comprobante tributario real ni significa que toda la seguridad de producción esté cerrada.

CAMBIOS Y COMPROBACIONES REALIZADAS
- Se actualizó la API compilada junto con su fuente y dependencias, con respaldo previo y reversión prevista durante el despliegue.
- La emisión ya no depende de una key ni del antiguo cupo de una boleta. Conserva validación de pedido pagado, importe, configuración, certificado y reintentos.
- Se corrigió SOAPAction por operación (urn:sendBill, urn:sendSummary, urn:getStatus), conforme al WSDL publicado de SUNAT.
- Certificado existente reconocido: certificado.p12. Clave válida, firma y vigencia comprobadas; vence el 19/11/2029 a las 14:34:50 UTC.
- Los hashes de .env y de los tres archivos persistentes del certificado coinciden antes y después de la intervención. No se reemplazaron con archivos locales.
- Diez archivos clave desplegados, incluidos fuente, compilación y pruebas, coinciden con los hashes de la entrega local.
- API /health: HTTP 200, base de datos conectada. Ruta de emisión sin autenticación: HTTP 401, según lo esperado. CORS permite al dominio del negocio. Handshake de tiempo real y una consulta de ruta geográfica responden.
- Se ejecutaron 14 pruebas automatizadas de firma, PDF, CDR, emisión sin licencia, reintentos, importes y estados de WhatsApp: todas pasan en local y en el servidor.
- Boleta y factura ficticias fueron aceptadas por SUNAT Beta con código 0, XML, PDF y CDR. La factura tuvo inicialmente un HTTP 401 y fue aceptada al repetirla por separado. Las pruebas usan numeración independiente y no consumen correlativos reales.
- La consulta getStatus en producción con un ticket ficticio devolvió HTTP 200 sin cuerpo, incluso con SOAPAction correcto y una variante WS-Security. No se diagnosticó por ello una contraseña incorrecta ni se certificaron permisos SOL: la respuesta no es concluyente.
- No se emitieron comprobantes tributarios reales ni se reenviaron en lote los pedidos históricos. No se modificó el estado de los comprobantes anteriores.
- WhatsApp permanece inactivo por indicación del propietario. La sesión consultada devolvió 404. La API y los archivos de frontend entregados solo intentan enviar si la sesión reporta WORKING. Una sesión desconectada no se reporta como envío pendiente. No se creó una cola para remitir mensajes al reconectar.
- No se enviaron mensajes reales de prueba. La comprobación posterior de inicio de sesión utilizó únicamente el acceso facilitado por el propietario.
- Se habilitó pm2-root.service para el arranque automático y se guardó la lista PM2. Se verificó enabled; no se reinició el servidor para probar un arranque completo.

PENDIENTES PRIORITARIOS PARA CERRAR PRODUCCIÓN
P0 - Acceso: el código existente acepta un respaldo universal y lo expone en respuestas de acceso. Sustituirlo por un flujo seguro y un canal alternativo verificado. No se deshabilitó silenciosamente mientras WhatsApp está inactivo porque bloquearía el acceso actual. Antes de captar clientes digitales, preparar y verificar la transición.
P0 - Tiempo real: la implementación permite unirse a salas por nombre sin verificar identidad ni permisos. Incorporar autenticación, autorización por sala, límites y cierre por sesión; probar cocina, caja y seguimiento.
P0 - SQL: el puerto 1433 es alcanzable desde fuera, comprobado con conexión TCP al servidor. Restringirlo a loopback/red privada o a IP administrativas expresamente necesarias y comprobar API y administración después. El firewall UFW activo no evitó esa exposición de Docker. No se modificaron reglas que pudieran cortar un acceso administrativo no inventariado.
P0 - Dependencias: npm audit --omit=dev informó 12 paquetes afectados (1 crítico, 8 altos, 2 moderados, 1 bajo). Es un reporte de dependencias, no evidencia de explotación. Actualizar en una entrega de seguridad, revisar compatibilidad de MinIO y volver a validar acceso, archivos, SQL y tiempo real; no aplicar un downgrade mayor automático a producción.
P1 - SUNAT real: confirmar en SOL permisos del usuario secundario y registro del certificado; comprobar una venta real identificada y revisar su CDR de aceptación, manteniendo el correlativo y la evidencia. Beta valida estructura y no acredita esos permisos de producción.
P1 - Continuidad: automatizar respaldos SQL completos y de log acordes con recuperación FULL, copia cifrada externa, alertas y prueba de restauración en un entorno independiente. Hoy existe el respaldo puntual verificado de esta intervención.
P1 - Hosting: publicar 1.6.61 de las cuatro aplicaciones y corregir caché. Comprobar versiones, inicio de sesión y acceso desde móvil tras subir.
P1 - Operación: revisar individualmente pedidos activos antiguos y la boleta rechazada existente. No emitir masivamente los históricos ni cancelar estados por antigüedad sin revisión.
P2 - Rendimiento: los builds avisan de algunos bloques JavaScript mayores de 500 kB. Medir carga móvil y dividir módulos según uso; no se hizo prueba de carga concurrente en la base activa.
